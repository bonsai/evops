2. UC2「画像を評価する」

前提条件生成画像と対応する実行IDが存在し、有効な評価条件・評価器を選択できる。
基本フロー
  1. 画像と実行IDを受け取る。
  2. 形式・可読性・評価条件を検証する。
  3. 評価器を実行し、項目別スコアと根拠を得る。
  4. 評価器・設定の版と結果を保存する。
  5. 結果と注意事項をクリエイターに表示する。
例外画像欠損・評価器エラー・出力形式不正を区別して記録し、未評価を合格扱いにしない。
事後条件評価結果が画像・実行ID・評価条件の版に紐づき、再確認できる。

3. UC3「修復案を作成する」

前提条件評価結果が存在し、改善対象と評価根拠を特定できる。
基本フロー
  1. 低評価項目と根拠を確認する。
  2. 変更可能な条件（プロンプト、マスク、seed等）を選ぶ。
  3. 変更候補と期待効果・副作用を提示する。
  4. クリエイターが採否を決め、決定を記録する。
例外根拠不足や評価の不一致がある場合は、自動修復を確定せず追加確認を求める。
事後条件修復案・採否・理由が元画像と実行IDに紐づく。元画像を上書きしない。

4. 関係と優先度の読み方

  • UC1→UC2：生成後に評価を実行する業務フロー。UMLの《include》とするのは、UC1の成功時に毎回必須とする仕様を採用した場合に限る。
  • UC3：評価結果に問題があるときだけ実行するため、UC1またはUC2からの《extend》候補。矢印の向きと拡張条件を図で明記する。
  • UC4〜UC6：独立した利用目的として記載し、別のUCを単に画面操作として重複定義しない。
  • 優先度1：中核機能・実演対象。優先度2：重要だが、基本動作の成立後に実装する。
設計上の注意：外部のVLMはシステムと連携する支援要素であり、利用者の目的を直接表すアクターとして描くかは境界の定義に依存する。UC図・本文・実装の責務を一致させる。

5. 要求モデルの整合性チェック

  • すべてのUC名が「動詞＋目的語」で、利用者または外部システムの目的を表す。
  • UC1の成果物ID・実行IDがUC2の入力へ引き継がれる。
  • 評価結果には評価条件・評価器の版が残り、未実行と低評価を区別する。
  • 修復案は提案として記録し、人の承認なしに元画像を上書きしない。
  • 履歴・レポートで生成条件と評価結果を同じ実験単位で追跡できる。
  • 《include》／《extend》は業務上の必須性・条件性に基づき、線の都合で付けない。
