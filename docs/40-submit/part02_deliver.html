UC2 — 画像を評価する

前提：生成画像と実行IDがあり、有効な評価条件・評価器を選べる。

  1. 画像・実行IDを受け取る。
  2. 形式と評価条件を検証する。
  3. 評価器を実行し、項目別スコアと根拠を得る。
  4. 評価器・設定の版と結果を保存し、表示する。

例外：画像欠損や評価器エラーは未評価として記録し、合格扱いにしない。

UC3 — 修復案を作成する

前提：改善対象と評価根拠を特定できる。

  1. 低評価項目と根拠を確認する。
  2. プロンプト・マスク・seed等の変更候補を作る。
  3. 期待効果と副作用を示す。
  4. クリエイターが採否・理由を決めて記録する。

例外：根拠不足や評価不一致がある場合は、自動修復を確定せず確認を求める。

関係と優先度
  • UC1→UC2は業務上の後続関係。UC1成功後に必ず評価する場合のみ《include》を採用する。
  • UC3は問題がある場合だけ行うため、《extend》の候補。拡張条件と矢印方向を図で明記する。
  • 優先度1は中核機能・実演対象、2は基本動作の成立後に実装する機能。
整合性チェック
  • UC1の成果物ID・実行IDがUC2に引き継がれる
  • 評価結果に評価条件・評価器の版が残る
  • 修復案は元画像を上書きせず、採否を記録する
  • 履歴・レポートで生成条件と評価結果を追跡できる
  • 《include》／《extend》を必須性・条件性で判断する
設計上の注意：VLMは評価を支援する外部システムとして扱う。UC図・本文・実装の責務を一致させ、未実行・失敗・低評価を区別する。
納品物 2 — 分析モデル

ロバストネス分析（UC1：画像を生成する）要求をBoundary／Control／Entityの責務へ分解する。

15
FIG 2-1
UC1「画像を生成する」のロバストネス図
図 2-1　緑＝Boundary、黄＝Control、青＝Entity。分析段階の責務を示す。
Boundary

生成フォームと結果表示。入力、進捗、成功・失敗状態を利用者に伝える。

Control

入力検証、実行ID発行、エンジン呼び出し、処理状態と例外を調整する。

Entity

生成条件、実行履歴、成果物参照、ログを実行IDに紐づけて保存する。

基本メッセージ順序
  1. 条件を入力し、生成要求を送信する。
  2. 生成制御が検証し、実行IDと設定を記録する。
  3. エンジン接続が生成処理を呼び出す。
  4. 画像・ログ・状態を履歴へ保存する。
  5. 結果表示が完了または失敗を通知する。
分析上のルール
  • Boundaryは入出力に集中し、業務判断やDB操作を抱え込まない
  • Controlがフローを調整し、Entityは保持データを表す
  • 入力不備・生成失敗・保存失敗を区別する
  • 実行IDから設定・画像・ログを追跡できる
引き渡し：分析クラス候補は設計クラスと同一とは限らない。p16で属性・操作を整理し、p17でメッセージ順序を検証する。

from dataclasses import dataclass
from datetime import datetime

@dataclass
class Record:
    """台帳の 1 項目を表すエンティティ。"""
    _id: int
    _name: str
    _updated: datetime

    def __post_init__(self) -> None:
        self._updated = datetime.now()

    @property
    def name(self) -> str:
        return self._name

    @name.setter
    def name(self, value: str) -> None:
        if not value.strip():
            raise ValueError("名称は必須です")
        self._name = value
bservice/record_service.py — 《control》
from domain.record import Record
from repository.base import RecordRepository

class RecordService:
    """登録・検索のユースケースを実行する。"""
    def __init__(self, repo: RecordRepository) -> None:
        self._repo = repo

    def register(self, name: str) -> Record:
        record = Record(_id=self._repo.next_id(), _name=name)
        self._repo.save(record)
        return record

    def search(self, keyword: str) -> list[Record]:
        records = self._repo.all()
        return [r for r in records
                if keyword in r.name]

補足設計 — EVOPS 外部実験環境

Kaggle MLOps 連携学習・評価は Kaggle、実験の正本と履歴は EVOPS に置く。

25
システム境界と責務
EVOPS（正本）
  • 生成物・人間評価を記録
  • SQLite / JSONL で実験履歴を管理
  • 学習対象データをエクスポート
  • 予測結果を取り込み、比較レポートを作成
Kaggle Notebook（実験）
  • データセットのバージョンを固定
  • 特徴量抽出・学習・検証を実行
  • MAE / RMSE などでモデルを評価
  • 予測結果・指標・モデル情報を出力
人間（判断）
  • 予測と実際の評価の差を確認
  • 採用するモデルと閾値を決定
  • 自動採用は検証後に段階導入
最小データ契約（JSONL）
{
  "sample_id": "stable-id",
  "asset_uri": "dataset-relative/path",
  "human_score": 0.0,
  "split": "train",
  "schema_version": "1"
}

学習時は train / validation を分離する。人間評価がないサンプルは教師あり学習に混ぜない。個人情報や秘密情報はアップロードしない。

実験フロー
  1. EVOPS からデータセットをエクスポートする。
  2. Kaggle Dataset と Notebook のバージョンを記録する。
  3. ベースライン（平均予測など）と ML モデルを比較する。
  4. OOF / validation 予測、指標、設定を成果物として保存する。
  5. 予測結果を EVOPS に戻し、人間評価との差を分析する。
MLOps の合格条件
  • 同じデータ・設定で実験を再現できる
  • データ版・Notebook版・モデル版が追跡できる
  • 人間評価との誤差をベースラインと比較する
  • モデル未使用でも既存 EVOPS が動作する
  • 自動採用前に人間が結果を確認できる
設計原則：Kaggle は GPU を使う学習・実験環境。EVOPS の SQLite / JSONL と評価ループを置き換えない。連携はファイル契約で疎結合に保ち、まずは CSV / JSONL の入出力から始める。
実装ワークフロー — 生成・評価・記録・改善

Kaguru Agent × Kaggle × EVOPS生成→評価→記録→改善。人間の判断を挟み、次の生成へつなぐ。

26
システム構成図
受け渡しデータ契約

各段階を直接結合せず、安定したIDとファイル形式で接続する。

{
  "schema_version": "1",
  "run_id": "run-001",
  "sample_id": "image-001",
  "asset_uri": "images/image-001.png",
  "concept": "target concept",
  "prompt": "generation prompt",
  "generator": "kaguru-agent",
  "human_score": null,
  "clip_score": null
}
  • 生成側：画像、prompt、設定、sample_idを出力
  • 評価側：Tier-1の形式・輝度チェック、Tier-1.5のローカルVLM、Tier-2のKaggle指標をsample_id単位で出力
  • EVOPS：入出力を結合し、実験履歴を保管
  • 改善側：提案した変更と採否・理由を記録
重要：Tier-1.5はローカル軽量VLMによる視覚チェック。CLIPスコアはプロンプトとの相対的な類似度で、画像品質や人間の好みを直接表すものではない。人間評価との校正前に単独で画像を選別・自動採用しない。
完了条件
  • 同じsample_idから画像・生成条件・評価結果を追跡できる
  • 画像生成が失敗しても、他のサンプルの処理を継続できる
  • 評価結果にNotebook版・データセット版・実行設定が残る
  • 人間評価とCLIP評価を並べて比較できる
  • 改善提案・採否・次回条件を記録できる
  • KaggleやKaguru Agentが停止してもEVOPSの履歴は失われない
責務の境界：Kaguru Agentは画像生成、KaggleはGPU評価、EVOPSは正本と履歴管理、evolve_loopは改善候補の提案を担当する。まずは画像・JSONL・CSVの受け渡しで動かし、各サービスのAPI連携は必要になってから追加する。
