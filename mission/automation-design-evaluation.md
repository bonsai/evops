# 自動化と人間領域の分離

## 前提

> 「自動化が課題だが、設計と評価は人間がやる。テストも。しかし教えれば機械でもできる。」

## 人間の領域

| 領域 | 内容 | 理由 |
|------|------|------|
| コンセプト設計 | 何を作りたいか、どんな世界観か | 目的・文脈は人間しか持てない |
| 評価基準の策定 | 「良い」とは何かを定義する | 美的・倫理的価値観の反映 |
| テスト設計 | どのような入力で何を確認するか | 品質保証の責任所在 |
| 最終判定 | 出稿 / 採用 / 棄却 | 責任を持つ主体は人間 |

## 機械に教えた後に任せる領域

| 領域 | 内容 | 必要な"教え" |
|------|------|-------------|
| 反復生成 | プロンプトから大量バリエーション | プロンプト戦略、禁止事項 |
| 前処理 | SVG 読み込み、3D 化、レンダリング | Blender bpy の手順書 |
| 評価補助 | 指標計算、類似度、トレンド検出 | 評価関数と教師データ |
| 可視化 | スコア分布、履歴、相関 | 可視化ルール |
| ナレッジ蓄積 | 過去の成功/失敗パターンの検索 | DB 化、タグ付け、ベクトル化 |

## 教える方法

1. **ルールベース**: 明示的なガイドライン、チェックリスト、禁止パターン
2. **例示（few-shot）**: 良い例 / 悪い例をペアで提示
3. **数値化**: 人間の評価をスコア化し、機械が学習できる形に
4. **フィードバックループ**: 生成 → 人間評価 → 機械が重み更新 or ナレッジ登録

## リスクと対策

| リスク | 対策 |
|--------|------|
| 機械が独断で変なものを生成 | 人間の承認ゲートを必ず挟む |
| 評価指標が目的をすり替える | 指標は定期的に人間が見直す |
| 生成ばかりで質が下がる | 多様性・意外性を指標に含める |
