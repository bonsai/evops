アクターの留意点
  • 必ずシステムの外側に存在する。田中さんではなく「○○利用者」という役割で表す。
  • 実在の人物名は使わない。
  • 「時刻」がアクターになるなら ⇔ バッチ処理がある。日時指定の処理も表現する。
  • インストール・起動／停止・保守を担当する実体もアクター。
境界の判断基準
問い答え
誰が（何が）使うか
どこで責任を切るか
保存データはどこ
UI は内側か外側か

原則：「入力値の検証」と「表示」はシステム内。利用者本人の手作業は外。

講義の事例（酒問屋）

顧客が直接注文する場合 → 境界は「注文を受ける」。
受付係が処理する場合 → 境界は「受付処理」。Swing などで自動化するなら内側。

→ 自分のシステムで同じ検討を 1 度書く。

《include》

毎回必ず実行される共通処理。起点 UC から include 先へ破線矢印（依存）。

《extend》

条件によって条件付きで実行。拡張元の動作から <<extends>> の破線矢印。

命名の注意

主語は「動詞 ＋ 目的語」（例「検索する」「通知する」）。名詞・形容詞は不可。

納品物 2 — 分析モデル

ロバストネス分析（ロバストネス図）3 種類の分析クラス：バウンダリ／コントロール／エンティティ。

15
FIG 2-1
ロバストネス図　／　UC1「」の実現
図 2-1　ロバストネス図　／　凡例：緑＝バウンダリ、黄＝コントロール、青＝エンティティ
《boundary》バウンダリ

アクターとの接点。ユーザー IF／システム IF／デバイス IF の 3 種。画面やフォームの抽象化。

《control》コントロール

複数のクラスをまたぐ動作を調整する。UC 開始で生成、終了で破棄される。

《entity》エンティティ

永続性のある情報。複数の UC で共有される。get／set のみが基本。

通信ルール：アクター⇔バウンダリのみ／バウンダリ⇔コントロール／エンティティ⇔コントロールのみ。 エンティティ同士が直接通信するのは禁止。
